## コード確認から分かった流れ

- `apps/automator/app/src/usecases/process_podcast_workflow.py`：音声処理→議事録→紹介文→R2音声・RSS公開→保存・SNS案生成。SNS生成の直接入力は紹介文。SNS生成に失敗する前にRSSが公開され得る順序なので、処理全体の失敗を未公開と同一視しない。
- `apps/automator/app/src/infrastructure/ai_analyzer.py`：紹介文はtemperature 0.3 / max_output_tokens 12000、SNSは0.7 / 4000で構造化生成。形式検証は事実の正確性の証明ではない。
- `apps/ui/src/server/chat/chat-service.ts`：通常検索は上位12チャンク＋補足情報。空ヒット・例外時は全ナレッジ。会話ありでは検索質問書換えの生成も行う。
- `knowledge.ts`：議題案とSNS案を補足。SNSは未投稿を除外しない。元データを読む量と、モデル入力へ採用する文字数は異なる。
- `session-repository.ts`：履歴保存は `chat_sessions/{userId}/sessions/{sessionId}`。Podcast識別子は持たない。同一利用者のチャンネル切替時のUI動作と、権限剥奪後の履歴方針は未確認。
- `minutes-context.ts`：本文コンテキストの基本予算120000文字、通常経路の補足は追加40000文字。区切り・システム指示・会話履歴は別なので、これをリクエスト全体の厳密上限と説明しない。
- チャットAPIは50メッセージ、各10000文字まで。利用回数の確認と記録が別処理であり、原子的な枠の確保ではない。

## 公開方針案（設定確認前）

Xは事前承認なしの自動投稿を継続する。未承認という理由だけでは失敗にしない。対象Podcastと認証情報の対応、予定時刻、停止状態が条件を満たすことを確認対象にする。編集・削除と送信の競合、送信成功後の保存失敗、二重投稿防止は未検証。

音声/RSSは既存コードの自動公開経路を記録した段階。アップロードを公開許可として扱えるか、誰がどこで停止するかは運用確認が必要。任意の承認機能が本番に存在するとは書かない。RSSから削除しても取得済み音声の回収は保証できない。

## ログ・利用量・権限の対応案

現状：議事録・紹介文のDiscord通知、紹介文のログ出力、JSON解析失敗時の生成本文ログがある。生成日時、prompt_versionの固定値v1等もあるが、処理全体を追跡できる証拠はまだ揃っていない。

設計案：処理ID、Podcast/Episode、処理段階、モデルID、プロンプトハッシュ、参照元ID、公開先識別子、結果、入出力トークン、所要時間、試行回数を結び付ける。通常ログには本文・認証情報・署名付きURLを記録しない。合成評価の本文は評価記録に限定する。保存期間・閲覧者は運用確認後に確定する。

回数制限は同時実行時の枠確保をトランザクション等で原子的に行う修正が候補。費用の上限には回数だけでなく入出力量・追加モデル呼出しも含める。音声時間・サイズ、再試行回数、全体タイムアウトの実効設定は未検証。

Terraform上、バックエンドの複数処理は共通SAを参照し、`infra/iam.tf`にrun.admin、secretAccessor等がある。UIにも`infra/ui_iam.tf`でsecretmanager.adminが定義される。実際の付与権限とは区別する。音声処理・X投稿・議題生成の順に必要なAPI/Secretを列挙して分離を検討する。LLMがこれらの権限を直接使えるという証拠ではない。
