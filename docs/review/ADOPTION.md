## 2. 個別の判断材料

### F1（他番組の処理停止）

- **前回の修正の動作**：ジョブの `PODCAST_ID` と異なる番組のアップロードは、公開の前にエラーで止める。
  - 公開だけでなく、議事録・索引などの**内部向けの処理もすべて止まる**（暫定策）。
- **前提の変化**：develop は、番組ごとの RSS（`4b145d5`）を持つようになった。今回の I-02 で、公開音声のキーも番組ID・エピソードIDで分かれる。
  - その結果、F1 の「既定番組の RSS に混ざる」という問題は、F1 を使わなくても大部分が解消する（I-02 を採用した場合。テストでは未確認）。
  - 一方で、他番組のアップロードは「番組自身の公開RSS・公開音声」として R2 に公開される。
  - dev はゲストモードが有効なので、ゲストのアップロードも公開されうる。
- **単純に F1 と I-02 の両方を取り込まないこと**：
  - F1 を入れると、I-02 で分けた番組ごとの公開は使われず、他番組の議事録作成も止まる。
  - F1 を入れないと、他番組の公開は許される。
  - 目的が違う（F1 は「既定番組以外を公開しない」、I-02 は「公開先を取り違えない」）。
- **決めてほしいこと**：
  1. 既定番組以外の番組を、R2・RSS に公開してよいか（dev・本番それぞれ。ゲストを含む）。
  2. 公開しない場合は、「公開だけを止め、議事録・索引は作る」方式に F1 を作り直すか（前回は、通話・録音機能の開発と重なるため保留）。
  3. `rss_feed_path` が NULL の番組が dev にあるか（`DEV_CHECK.md` §1。NULL の番組は既定のフィードに書き込む）。
- **推奨**：F1 は今回は取り込まない。I-02 の採用を先に決め、そのうえで公開方針を決める。

### F2（既定Xアカウントの限定と投稿の確保）＋ F3（SNS 編集APIの制御）

- **変更点**：
  - F2：
    - 既定の X アカウントは、`PODCAST_ID` の番組の投稿にだけ使う。
    - 送信前に、トランザクションで pending → posting を確保する。
    - 送信が成功した後に状態の記録が失敗したら、posting のまま残す。
    - `infra/promoter.tf` に `PODCAST_ID` を追加する。
  - F3：
    - 既存の投稿だけを更新し、ID の形式を検証する。
    - 利用者が設定できる状態は pending・posted だけにする。
    - posting の投稿は、状態を変更できない（409）。
- **機能・運用への影響**：
  - 認証情報のない番組の投稿は、既定アカウントで送らず failed になる。
  - 自動投稿は維持する（事前承認は追加しない）。
  - promoter ジョブの設定が変わる（Terraform、dev・本番）。
  - develop の tfvars では、promoter は dev で無効（`enable_promoter = false`）、本番で有効。そのため、dev では動作を確認できない。
- **前回から引き継ぐ残課題**（前回 merge-review より。今も未対応）：
  1. **予定日時の再確認漏れ（再現済み）**：一覧を取得した後に投稿を翌日へ延期しても、確保処理は pending かどうかしか見ないため、そのまま送信する。確保の中で最新の予定日時を確かめる修正と、テストが必要。
  2. **取消・編集の期限**：
     - 確保した後でも、本文の編集・削除が許可されている。
     - 「削除後の送信はすべて防止」とは説明しない。
     - 確保時点を取消期限にするなら、API・UI にも反映する。
  3. **一部送信・結果不明**：
     - スレッドの途中で失敗した場合や、通信エラーのときは、一部が公開済みでも failed になりうる。
     - 手動で再送する前の確認方法と、posting のまま残った投稿の復旧方法を決める。
     - 自動復旧や、完全な二重送信防止は実装していない。
- **決めてほしいこと**：残課題1〜3を、取り込みの前に直すか、取り込み後の課題とするか。

### F4（利用枠の確保をトランザクション化）

- **変更点**：
  - `reserveUsage` を追加する。プールから1つの接続を取り、`BEGIN` → 利用者・操作ごとの `pg_advisory_xact_lock` → 確認 → 記録 → `COMMIT` を行う。
  - chat・reindex・upload-url・recording の4か所で使う。現在の develop の利用箇所もこの4か所だけである。
- **接続方式との適合性**（コード確認）：
  - develop の `db-pool.ts` は2方式ある：`DATABASE_URL`（Supabase のプーラーを想定）による `pg.Pool`、または Cloud SQL コネクタ。
  - トランザクション内だけで有効なロックを、1つの接続で使うため、セッションモード・トランザクションモードのどちらのプーラーでも動く設計である。
  - dev の接続ポート（6543 か 5432 か）と、Supabase での実行は未確認（`DEV_CHECK.md` §1）。
- **利用枠の消費タイミング**：
  - 従来と同じく、処理を始める前に記録する（処理が失敗しても1回と数える）。
  - 変わるのは「確認と記録の間に、ほかのリクエストが入らない」点だけである。
  - recording は開発中の機能で、その数行を変更している。
- **DB**：migration はない。
