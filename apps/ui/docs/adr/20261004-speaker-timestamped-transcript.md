# 話者・時刻つきの文字起こし（音声認識ベース）

## Context

エピソードの「文字起こし」は、Gemini に音声を 1 回渡して書かせた議事録だった。

- 目次の時刻（`0:16 ○○`）はモデルの推測なので、長い回ほど実際とずれる。
- Firestore の `transcripts` は議事録を 1,200 字ごとに切ったもので、`speaker: "unknown"`・`start_time: 0` の固定値。
- 話者名はプロンプトに直書き（小野、数森、高島）で、他のチャンネルには合わない。

ブラウザ収録（#166）では話者ごとのトラックが手に入るので、これを活かして話者と時刻を正確にしたい。

## Decision

- **時刻は音声認識から取る。** Speech-to-Text v2 の **`long` モデル**（asia-northeast1、BatchRecognize、ja-JP、単語ごとの時刻）を使う。
  - 2026-10 に dev の実データ（話者別トラック）で実際に試して決めた。
    - Chirp 2 の ja-JP は、us-central1 では「一般提供の終了」で 403 になり、asia-southeast1 では結果が 0 件だった。
    - Chirp 3 は全文が 1 件の結果にまとまり、時刻が付かなかった（単語の時刻にも、日本語の話者分離にも非対応）。
    - `long` は発話ごとの結果と単語の時刻を返し、台本の開始時刻と一致した。東京リージョンなので、音声が国外に出ない。
  - 費用は 1 分あたり約 $0.016。60 秒以下の音声は BatchRecognize の対象外なので、同期認識を使う。
  - モデルと地域は env（`SPEECH_MODEL` / `SPEECH_LOCATION`）で変えられる。Chirp の日本語対応が戻ったら切り替えを検討する。
- **話者**
  - ブラウザ収録では、mixer が作る話者別の位置合わせ済みトラック（ミックスと同じ時間軸）を、話者ごとに認識する。話者分離の推定が要らず、話者名も参加者の表示名がそのまま使える。
    - スピーカーで聞いている人がいると、相手の声がマイクに入り込み、同じ発話が 2 人分に出る。時間が重なり本文も似ている発話は、その区間の音量（RMS）が大きいトラックだけを残す。
  - アップロードされたミックス音声は、日本語の話者分離に対応した GCP の音声認識が無いため、各発話の話者を Gemini に音声を聞かせて推定させる（推定なので誤りはありうる）。登場人物は番組設定（`podcasts.cast_members`）から渡す。
- **議事録は文字起こし（テキスト）から作る。** `[m:ss] 話者: 発言` の行を Gemini に渡し、目次の時刻は文字起こしの時刻をそのまま使わせる。
  - Discord への投稿（`#N Meeting Transcript:`）の形式は変えない。アジェンダ生成がこの文言を境界に使っているため。
- **保存**
  - `transcripts` は 1 発話 = 1 ドキュメント（スキーマ仕様書 3.2 の形）。
  - 議事録は親ドキュメントの `minutes` に置く。
  - UI の一覧は `transcripts` を読まない（件数が多いため）。文字起こしタブを開いたときだけ読む。
- **音声認識に失敗したとき**（クォータ・障害）は、従来どおり Gemini に音声から議事録を作らせて処理を止めない。`transcript_meta.engine = gemini_audio` で区別できる。`SPEECH_ENABLED=false` で従来方式に戻せる。
- **音声認識が成功して発話が 1 つも無いとき**（無音・ミュートのまま収録した など）は、Gemini に回さずエピソードを失敗にする（「音声から発話を聞き取れませんでした」）。Gemini に無音を渡すと「音声記録が提供されていません」という返事が議事録になり、そのままタイトル・SNS 投稿・RSS まで作られてしまうため。Gemini の経路でも、会話が無ければ `NO_SPEECH` と返させて同じく失敗にする。
- **チャット用の索引は、エピソードが完成した時点でその番組の分を作り直す。** 毎朝 4 時の定期実行だけだと、できたばかりのエピソードについてチャットで聞いても翌朝まで答えられないため。automator が完了を記録したあと、UI の `/api/cron/reindex-minutes?podcastId=N` を定期実行と同じ `CRON_SECRET` で呼ぶ（Job の env は `APP_BASE_URL` と `CRON_SECRET`）。失敗してもエピソードは失敗にせず、定期実行で追いつく。

## Consequences

- 処理時間が延びる。BatchRecognize は 60 分の音声で数分かかる。結果を応答で受け取る（inline）設定は 1 リクエスト 1 ファイルまでなので、ブラウザ収録は話者ごとにリクエストを出して並行に待つ。
- 費用が増える。60 分・4 人の収録を話者ごとに認識すると約 $1。
- 話者別トラックを Speech に渡すため、作業用の GCS バケット（7 日で削除）を設けた。入力バケットに置くと既存パイプラインが起動してしまうので、使い分けている。
- 既存のエピソードは作り直さない。UI は、以前の形式（議事録の分割）も議事録として表示し続ける。
