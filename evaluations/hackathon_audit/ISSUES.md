## 詳細

### I-01 全却下→原音声公開の状態を保存できない（A）
- **修正前の再現**（`evidence/before/`）：`run-ui.sh` の V1-UI-08。リポジトリの migrations で作った DB で、すべての指摘を却下した。
  - `UPDATE episodes SET status='awaiting_publish_confirmation'` が `value too long for type character varying(20)` で失敗した。
  - 旧経路は 500、統合経路は 409 を返した。原音声公開（confirm-original-publish）は 409 のまま進めなかった。
- **修正**（`b053ab5`）：`apps/ui/migrations/015_widen_episode_status.sql` で列を `VARCHAR(40)` に広げる。広げるだけなので、既存の値は変わらない。
- **修正後の確認**（エミュレータ。migrations を 015 まで適用した DB）：V1-UI-08 で全却下すると公開確認へ進み、原音声公開ジョブが1回だけ起動した。
- **残る点**：dev・本番の DB に 015 が適用されるのは、develop・main への CD（または PR プレビュー）の実行時である。現在の dev の列定義は未確認（`DEV_CHECK.md` で確認する）。

### I-02 エピソード番号の重複と公開音声の上書き（A）
- **修正前の再現**（`evidence/before/`）：`test_episode_numbering.py`（実際の `PostgresEpisodeRepository` を使用）。
  - 番号は公開のたびに `COUNT(*)+1` で決まり、未公開の行も数えていた。
  - 3件アップロード済みの番組では、3件とも `#4`・`{prefix}/ep/4/audio.mp3` に書き込み、後の公開が前の公開音声を上書きした。
- **修正**（`fcfce23`）：
  - `migrations/016_add_episode_number.sql` で `episodes.episode_number` を追加する。既存行は、タイトル先頭の `#番号 ` から補完する。
  - 番号は処理の開始時に一度だけ採番する（`assign_episode_number`）。番組単位の advisory lock 内で `COALESCE(episode_number, MAX+1)` を使うので、再処理しても番号は変わらず、同時に処理しても重複しない。
  - 公開音声のキーを、変更されないIDで決める：`{prefix}/podcasts/{番組ID}/episodes/{エピソードID}/audio.mp3`。編集版は同じ場所の `renditions/{計画ID}.mp3`。番号や公開順に依存しない。
- **修正後の確認**（エミュレータ）：
  - V1-10：E1・E3 を公開した後に、承認待ちだった E2 を原音声で公開した。キーは3件とも異なり、番号は 1・2・3 になった。
  - V1-11：同じ回を再処理しても番号とキーは同じだった。既存の公開回（旧形式のURL、`#7`）の行は変わらず、新しい回は `#8` になった。
- **既存の公開URL・RSSへの影響**：
  - 公開済みの回の `audio_file_path` は変更しない。RSS の再構築は DB の `audio_file_path` を読むため、既存の配信URLはそのまま使える。
  - R2 上の旧形式のオブジェクト（`ep/{n}/audio.mp3`）は削除しない。
  - 修正前にすでに上書きされていた回は、この修正では戻らない。dev で該当する回があるかは未確認。
- **残る点**：
  - 処理が途中で失敗した回にも番号が割り当たるため、番号に欠番が出うる。
  - 番号の一意制約は付けていない（既存データの重複が補完で入りうるため）。重複しないことは、採番時のロックで担保している。

### I-03 再監査APIに状態の前提条件がない（A）
- **修正前の再現**（`evidence/before/`）：V1-UI-01（API）と V1-02（ワークフロー）。
  - `retry-audit` は状態を問わず `auditing` に更新した。
  - 再監査で指摘が出なければ、前回の未判断の指摘・訂正介入を空で上書きし、自動公開した。
- **方針**：再監査は禁止しない。以前の指摘・判断・実行中のジョブと新しい監査結果の関係を、次のように整理した。
  1. **実行中のジョブ**：処理中・監査中・編集中の回は再監査できない（409）。ただし、7時間を超えて更新がない回は、止まったジョブとして再監査を認める（ジョブの上限は 25200 秒）。公開済み（completed）も再監査できない。
  2. **再監査できる状態**：failed、awaiting_approval、awaiting_publish_confirmation。
     - 状態は条件付き更新で1回だけ切り替える。そのため、同時に押されてもジョブは1件になる。
     - ジョブの起動を見送った場合は、元の状態に戻す。
  3. **以前の指摘と判断**：再監査の前に、指摘・訂正介入・統合レビュー（判断と版）を `review_history/{id}` に複製し、件数も記録する。消さない。
  4. **新しい監査結果**：
     - 指摘があれば、従来どおり承認待ちになる。以前の版番号とは一致しないため、以前の判断で作った編集計画は使えない。
     - 指摘がなくても、以前に確認事項があった回は自動公開しない。公開確認待ち（awaiting_publish_confirmation）にして、状態だけを通知する。
- **修正**（`f8c4598`）：`markEpisodeAuditing` の条件付き更新、`restoreEpisodeStatusAfterSkippedAudit`、`FirestoreManager.archive_review`、ワークフローの Step 2.5、`mark_awaiting_publish_confirmation`。
- **修正後の確認**：
  - V1-UI-01（エミュレータ）：処理中・公開済みの回は 409。failed・承認待ち・公開確認待ち・止まったジョブの回は再監査できた。
  - `test_reaudit_archive_emulator.py`（Firestore エミュレータ）：以前の判断が履歴に複製されることを確認した。
  - V1-02（モック）：再監査で指摘なし → 公開せず、確認待ちになった。
- **残る点**：
  - 履歴（`review_history`）は画面に表示していない。Firestore には残るが、利用者が以前の判断と比べる画面はない。
  - 7時間の判定は時刻に基づく推定である。実際にジョブが動いているかは確認していない。

### I-04 訂正介入だけの回は反映も原音声公開もできない（A）
- **修正前の再現**（`evidence/before/`）：V1-UI-09、V1-UI-04。
  - 訂正介入パネルの「カットイン編集を実行」は、外部編集サービス（`AUDIO_EDITOR_URL`）を呼んでいた。infra に定義がないため 503 になった。
  - 全却下しても状態が変わらず、原音声公開へ進めなかった。
- **修正**（`dbfceea`）：
  - 判断と公開の条件を、`apps/ui/src/server/policy/review-gate.ts` にまとめた。
    - **編集**：未判断が0件で、承認が1件以上ある。
    - **公開確認へ進む**：確認事項が1件以上あり、すべて却下されている。
    - **原音声の公開**：未判断が0件で、すべて却下されている。
  - この条件を、統合レビューの保存、訂正介入の保存、旧判断API、原音声公開の各経路で使う。
  - 訂正介入パネルの「カットイン編集」（`apply-interventions`）は、外部編集サービスを呼ばない。統合経路と同じ手順（版の確認 → 編集計画の固定 → 自動処理ジョブ）で編集する。`AUDIO_EDITOR_URL` は使わなくなった。
  - ポリシー指摘が0件で公開確認待ちの回でも、原音声公開の画面を表示する。
- **修正後の確認**（エミュレータ）：
  - V1-UI-09：訂正介入だけの回で承認すると、固定された編集計画（corrections 入り）が作られ、ジョブが1件起動した。
  - V1-UI-04：全却下すると公開確認へ進んだ。
  - V1-UI-03：判断の順序に依存しない。
  - V1-UI-10：通常の「編集して承認」は動いた。一部だけ判断した状態では、パネルからの要求を止めた。
- **残る点**：ブラウザでの画面操作は確認していない（API とコンポーネントの配線のみ）。

### I-05 旧判断APIが未判断の訂正介入を無視する（A）
- **修正前の再現**（`evidence/before/`）：V1-UI-02。統合レビューがまだ無い回では、訂正介入が未判断のまま公開確認へ進み、原音声公開のジョブが起動した。
- **方針**：旧API（`review-policy-findings`）は削除せず、残した。そのうえで、公開へ進む条件を統合経路と同じにした（I-04 の `review-gate.ts`）。
- **修正**（`dbfceea`）：
  - 旧API・原音声公開API の両方で、未判断や承認済みの確認事項が残っていれば進めない（409）。
  - 自動処理ジョブ側も、原音声公開の前に、保存された指摘・訂正介入がすべて却下済みかを確かめる（`_assert_all_review_items_rejected`）。そうでなければ停止する。
  - これにより、DB の状態を直接書き換えても公開されない。
- **修正後の確認**：
  - V1-UI-02（エミュレータ）：旧APIで指摘をすべて却下しても、訂正介入が未判断なら公開確認へ進まない。状態を強制的に公開確認待ちにしても、原音声公開は 409 だった。
  - `test_reaudit_review_boundary.py`（モック）：ジョブ側の停止を確認した。

### I-06 訂正台詞の再検査がない（A）
- **再現**：V2-05、V2-UI-01。
- **実結果**：代替音声の台詞は、合成・録音の時点でローカルPII・機密語・Jev の検査を受ける。一方、訂正介入の台詞（Gemini 生成。利用者が編集できる）は検査されない。機密語を含めて承認すると、編集計画にそのまま入り、編集時に合成・挿入され、編集後の文字起こしと再生成される議事録にも入る。
- **影響**：主張「機密語の除去」を、訂正台詞の経路から崩しうる。AIの訂正文に新しい誤りが入った場合も、自動では止まらない。
- **提案**：`PROPOSALS.md` §1。検出したら一律に禁止するのではなく、検査結果を表示し、変更があれば再確認・再承認を求める。既存の版管理と組み合わせる。未実装。

### I-07 機密語の照合が完全一致のみ（B）

- **推奨修正**：NFKC 正規化と空白除去を照合の前に行う。表記ゆれの登録を UI で案内する。
- **運用での限定**：機密語に読み・表記ゆれを併せて登録する。

### I-08 ローカルPII検出の範囲（B）

- **推奨修正**：GiNZA の人名ラベルを Presidio の PERSON に対応付ける。メールのパターンを追加し、検出範囲を単語境界まで広げる。
- **説明での限定**：「ローカル検出は電話番号・郵便番号・URL・住所の一部の定型パターン」と書く。

### I-11〜I-18
- **I-11**：Gemini の裏取りで「正しい」「概ね正しい」と判定されると記録も残さずに除外するため、AIの誤判定を人が見つけられない。除外した発話と根拠を画面に「AIが正しいと判断」として残すことを推奨する。

- **I-13**：外部公開の許可は、番組単位の監査の有効・無効だけ。エピソードごとの公開許可や予約はない。
- **I-14**：費用・外部送信の説明に影響する。「ローカルで判断できない発話だけを Jev に送る」構成ではない。
- **I-15**：監査トレースは障害解析に有用だが、保存期間・閲覧者を説明する必要がある。
- **I-16**：I-04 の修正で、訂正介入の保存時にも公開確認への遷移を判定するようにした。V1-UI-03 で、順序に依存しないことを確認した（エミュレータ）。
- **I-17**：`render_policy_audio` の接合部に短いフェードインを加える。
- **I-18**：承認画面で「根拠なし」を明示する。
- **I-19**：`infra/job.tf` は `DISCORD_WEBHOOK_INFO_URL`・`DISCORD_WEBHOOK_ERROR_URL` に Secret の値（`secret_data`）を直接入れている。このため、ジョブ定義（Cloud Run の設定画面・`gcloud run jobs describe`）と Terraform の state に URL が平文で残る（コードに「削除予定」の TODO がある）。URL を知っていれば、誰でもそのチャンネルに投稿できる。`secret_environment_variables` に移すことを推奨する。dev の実際の設定は未確認。確認では値を表示しない（`DEV_CHECK.md`）。
