## 2. 代表ケース（記事に使える具体例）

### ケース1：全部「却下」したのに、元の音声を公開できない（I-01）

- **入力・操作**：
  1. 合成エピソードの発話に、機密語「スイレン742」のポリシー指摘が付いた状態にする。
  2. 配信者が指摘をすべて「却下」し（AIの指摘は不要と判断）、原音声のまま公開しようとする。
- **期待**：公開確認待ち（`awaiting_publish_confirmation`）に進み、原音声公開のジョブが1回起動する。
- **実際**：
  - 状態の更新が `value too long for type character varying(20)` で失敗した。
  - 旧経路は 500、統合経路は 409 を返し、原音声公開も 409 のまま進めなかった。
- **原因**：
  - 状態の列は、初期の migration（`002_add_episode_processing_state.sql`）で `VARCHAR(20)` と定義されている。
  - その後に追加した状態名 `awaiting_publish_confirmation`（29文字）に対応する migration がなかった。
  - 既存の単体テストは DB を差し替えていたため、列の長さでは失敗しなかった。リポジトリの migrations で作った実際の PostgreSQL で初めて失敗した。
- **修正**：migration 015 で列を `VARCHAR(40)` に広げる（既存の値は変わらない）。
- **再検証**（エミュレータ）：全却下 → 公開確認 → 原音声公開のジョブが1回だけ起動した。
- **残課題**：
  - dev・本番の列が手作業で広げられているかは未確認。広げられていれば、dev では動いていた可能性がある。
  - 修正が反映されるのは、マージ後の CD 実行時（または PR プレビュー時）。
- **記事での観点**：DB を差し替えたテストは通っても、実際のスキーマで失敗する。

### ケース2：後から公開した回が、公開済みの回の音声を上書きする（I-02）

- **入力・操作**：
  1. 番組に3件アップロードする（E1・E2・E3）。
  2. E2 は承認待ちのまま、E1 と E3 を公開する。
  3. その後、E2 を原音声で公開する。
- **期待**：3件がそれぞれ別の公開URLを持ち、番号は 1・2・3 になる。
- **実際**：
  - 3件とも `#4`、公開キー `{prefix}/ep/4/audio.mp3` になった。後の公開が前の公開音声を上書きした。
  - RSS の音声URLは同じキーを指すため、聴く人には別の回の音声が届く。
  - 1件ずつ公開しても、番号は `#2` から始まった。
- **原因**：
  - 番号は公開のたびに `SELECT COUNT(*) FROM episodes WHERE podcast_id=…` ＋1 で決めていた（`episode_repository.py:23`）。この件数には、未公開・処理中・承認待ち・失敗の行も入る。
  - 公開キーは、この番号から作っていた（`process_podcast_workflow.py:519`）。
  - キーの接頭辞は配備ごとに固定で、番組ごとではなかった。
  - 承認待ちという「公開を後回しにする状態」が加わったことで、公開順と番号のずれが表に出た。
- **修正**：
  - `episodes.episode_number` を追加する。処理の開始時に、番組単位のロック内で一度だけ採番する。
  - 公開キーを `{prefix}/podcasts/{番組ID}/episodes/{エピソードID}/audio.mp3` にする。
  - 既存の行は、タイトル先頭の `#番号` から補完する。
- **再検証**（エミュレータ、実際の DB 処理）：
  - 公開の順番に関係なく、キーは3件とも異なり、番号は 1・2・3 になった。
  - 再処理しても番号は変わらなかった。
  - 既存の公開回（旧形式のURL）は変わらなかった。
- **残課題**：
  - 失敗した回にも番号が付き、欠番が出うる。
  - 古い R2 オブジェクトは残る。
  - 修正前にすでに上書きされた回は戻らない。dev で該当する回があるかは未確認。
- **記事での観点**：人の承認を入れると「処理順＝公開順」という前提が崩れ、別の不具合が表に出た。

### ケース3：再監査をすると、人が判断する前の指摘が消えて自動公開される（I-03）

- **入力・操作**：
  1. 1回目の監査で機密語の指摘が付き、承認待ちになる。
  2. 判断する前に、再監査API（`retry-audit`）を呼ぶ。画面のボタンは失敗時だけ表示されるが、APIは状態を確認していなかった。
  3. 2回目の監査で指摘0件になる。Jev の判定は確率的なので、起こりうる。
- **期待**：人が判断していない指摘は消えず、公開もされない。
- **実際**：
  - API は、承認待ち・完了・編集中のどの状態からも監査中に戻し、ジョブを起動した。
  - 2回目で指摘が0件だと、前回の未判断の指摘を空で上書きし、そのまま自動公開した。
  - 編集中に呼ぶと、編集ジョブと並行して動いた。
- **原因**：
  - 再監査APIに、状態の前提条件がなかった。
  - ワークフローは、監査結果を毎回置き換えていた。「以前に人の確認対象があった」という情報を持っていなかった。
- **修正**（再監査そのものは禁止していない）：
  - **実行中の回**：処理中・監査中・編集中は 409。7時間を超えて止まった回だけは、再監査を認める。公開済みも 409。
  - **以前の判断**：再監査の前に、指摘・訂正介入・判断の記録を `review_history` に複製し、件数も残す。
  - **新しい結果**：
    - 指摘があれば、従来どおり承認待ち。以前の版で作った編集計画は使えない。
    - 指摘が0件でも、以前に確認事項があった回は自動公開しない。公開確認待ちにする。
- **再検証**：
  - [エミュレータ] 処理中・公開済みの回は 409 になった。再監査できる状態では、正常に動いた。
  - [Firestore エミュレータ] 以前の判断が履歴に複製された。
  - [モック] 2回目の監査が0件でも、公開しなかった。
- **残課題**：
  - 履歴を画面で見る方法はない。
  - 7時間という判定は推定。実際にジョブが動いているかは確認していない。
  - 古いジョブが後から完了した場合の扱いは、未検証の追加確認事項（`ISSUES.md` I-20）。
- **記事での観点**：AIの判定が確率的だと、「やり直し」が承認を飛ばす経路になる。

### ケース4：同じ「承認・却下」でも、経路によって公開の条件が違った（I-04・I-05）

- **入力・操作**：
  - **(a)** ファクトチェックの訂正介入だけが付いた回（ポリシー指摘0件）で、訂正を承認して「カットイン編集を実行」を押す。または、すべて却下する。
  - **(b)** 統合レビューがまだ作られていない回で、旧判断API（`review-policy-findings`）を使い、ポリシー指摘だけを却下する。訂正介入は未判断のまま残す。
- **期待**：
  - (a)：承認なら、訂正を入れた音声で公開される。全却下なら、原音声公開へ進める。
  - (b)：未判断が残る間は、公開へ進まない。
- **実際**：
  - (a)：
    - 「カットイン編集」は外部編集サービス（`AUDIO_EDITOR_URL`）を呼ぶ。infra に定義がないため 503 になった。
    - 全却下しても状態が変わらず、原音声公開へ進めなかった（統合パネルは、指摘0件の回では表示されない）。
  - (b)：訂正介入が未判断のまま公開確認へ進み、原音声公開のジョブが起動した。
- **原因**：
  - 承認・編集・公開の条件が、経路（統合パネル、訂正介入パネル、旧API、原音声公開API、ジョブ）ごとに別々に書かれていた。
  - 機能を足すたびに、一部の経路だけが新しい条件になっていた。
- **修正**：
  - 条件を `review-gate.ts` の1か所にまとめた。
    - 編集：未判断0件、かつ承認1件以上
    - 公開確認へ進む：確認事項が1件以上あり、すべて却下
    - 原音声公開：未判断0件、かつすべて却下
  - すべての経路で、この条件を使う。
  - 訂正介入パネルも、統合経路と同じ「版の確認 → 編集計画の固定 → ジョブ」で編集する（外部サービス不要）。
  - ジョブ側も、原音声を公開する前に、保存されている判断がすべて却下かを確かめる。
- **再検証**（エミュレータ・モック）：
  - (a)：承認すると、訂正入りの編集計画が固定され、ジョブが1件起動した。全却下すると、公開確認へ進んだ。
  - (b)：旧APIでは公開確認へ進まなかった。状態を強制的に書き換えても、原音声公開は 409、ジョブ側でも停止した。
  - 判断の順序に依存しない。
- **残課題**：
  - 画面での操作は未確認。
  - 訂正を入れた音声を、人が試聴していない。
- **記事での観点**：承認の条件をUIに書くのではなく、1か所に置いてすべての経路から使う。

### ケース5（未修正）：人が編集できる訂正台詞が、検査の外にあった（I-06）

- **入力・操作**：AIが生成した訂正台詞を、利用者が機密語「スイレン742」を含む文に書き換え、承認する。
- **期待**：代替音声の台詞と同じように、機密語・PII の検査を受ける。
- **実際**：
  - 台詞はそのまま編集計画に固定され、編集時に合成・挿入された。
  - 編集後の文字起こしと、再生成した議事録にも入った。
  - 一方、代替音声の台詞は、合成時に検査されていた（`verify_text`：ローカルPII・機密語・Jev）。
- **原因**：代替音声と訂正介入は、別々に追加された機能で、検査の入口が共有されていなかった。
- **修正**：**未実装**。提案は `PROPOSALS.md` §1。
  - 検出しても一律には禁止しない。
  - 検査結果を表示し、人が確認した記録を残して承認する。
  - 台詞を変更したら、再検査と再承認を求める。
- **再検証**：なし（未修正）。
- **記事での観点**：AIの出力を人が直せる箇所は、AIの出力と同じ検査を通す必要がある。

## 3. 実API評価なしで言えること・言えないこと

| 言える（範囲を書けば） | 言えない |
| --- | --- |
| 承認・却下・再監査・公開の経路で見つけた不具合と、修正候補での確認結果（エミュレータ・モック） | Jev・Gemini による監査の検出率・誤検知率 |
| 編集エンジンが、指定した範囲どおりにカット・無音化・置換すること（合成信号） | 実音声での範囲の精度、残留音がないこと |
| ローカル検出が、表記ゆれ・氏名を検出しないこと（ローカルで実行） | 「AIが機密情報を確実に除去する」 |
| 他番組のIDに差し替えても、取得・変更できないこと（エミュレータ） | 提出したサービスの動作保証（提出版が未確定） |
| 費用の構成：ローカル検出による Jev 呼び出しの削減はない。Jev と Gemini の役割分担はある | 総費用・削減率（未測定） |
